# auto 路由补强与 GitHub 明文密钥防泄露实施方案

日期：2026-10-20。检查基线：`4faa25dcff79156b2246cd9417d5ae0f5904ab0c`。

本方案可以直接交给 AI 执行。它是已完成的渠道优先级／模型得分分档改造之后的增量方案，不替换、不重复实施 `docs/auto-routing-priority-model-bands-plan.md`。实施前重新读取目标文件；已经修复的项目只核对，不覆盖其他改动。

本文只规定功能要求、代码修改、旧引用清理与交付标准，不列构建、运行测试或执行回归脚本的步骤和命令。本轮仅生成方案及脱敏审计记录，没有修改业务代码，没有提交或推送。

## 1. 不得改变的既有规则

- 保留：既有分组顺序 → 可用性过滤 → 渠道 priority 降序硬分层 → 同 priority 内跨渠道比较模型有效得分 → 模型得分分档 → 档内两级加权随机。
- 保留档宽 `0.01`、最高剩余得分锚定、包含边界及浮点误差容差；同档不再按精确分数决定先后。
- 保留先抽渠道、再抽该渠道本档模型。等渠道权重时，A 有 10 个模型、B 有 1 个模型，首次选择的渠道份额仍约各 50%。
- 模型权重显式 `0` 表示退出该分组 auto，包括后备；渠道权重 `0` 仍按原方案保留同档后备。
- 不恢复渠道聚合健康分、旧渠道健康分档、旧按分选渠旁路；不改变模型得分公式、失败判据、冷却阶梯及现有摘除作用域。
- 保留令牌模型权限、分组权限、显式渠道锁定、取消停止、响应已写出停止、计费及每日限额约束。
- 随机分流不是严格并发互斥，不新增“多个请求绝不命中同一模型”的承诺。

## 3. AUTO-01：永久摘除的并发与事务一致性

### 功能要求

1. 同一渠道 `a,b` 被两个请求分别摘除时，最终不能复活 `a` 或 `b`。
2. 更新 `channels.models`、重建 abilities、摘空后的渠道状态变更，应作为一个数据库原子操作；任一失败不得只提交其中一部分。
3. 模型已经不在 `models` 中，不能直接把所有情况视为完成：需要确认并修复遗留 ability；不允许继续路由被摘除模型。
4. 不删除渠道、不覆盖凭据、priority、weight、模型映射及其他无关配置。

### 代码要求

- 将数据库读改写移到 model 层的专用原子入口，service 负责失败分类、调用和结果日志。
- 使用事务内最新数据及并发冲突保护。建议采用比较旧模型列表的条件更新／CAS，并在冲突时重新读取后有限重试；不能只增加进程内互斥锁，因为多实例也会写同一数据库。
- SQLite 的写竞争／忙错误也必须有明确有限重试和失败返回；所有数据库分支均保持 SQLite、MySQL >= 5.7.8、PostgreSQL >= 9.6 兼容。
- 模型列表显式更新，保留最后一个模型删除后写入空字符串的能力；abilities 使用同一 `tx`，不得内部另开事务。
- 同步审阅 `channel.Update`、管理员编辑、批量修改、上游模型更新等模型列表写入口，避免使用旧快照重建 abilities 覆盖新状态。不能将全量旧 channel 对象写回。
- 修正空模型列表生成空字符串 ability 的情况：空模型名、空组名不得生成有效 ability。
- 事务提交后统一使路由快照及相关渠道缓存失效；不得在事务提交前失效后又被旧数据回填，提交后却不再失效。
- 冷却清理及成功日志放在数据库操作确认成功之后；摘除失败返回明确错误，不假报成功。

## 4. AUTO-02：候选配置原子发布

- 保持三种语义：分组键不存在＝默认候选；分组显式空列表＝该组禁用 auto 候选；模型权重显式 `0`＝该模型禁用 auto。
- 完成解析、清洗与校验后，一次性在写锁内替换完整配置；删除 `Clear()` 后再 `AddAll()` 的发布方式。
- 可为 `RWMap` 增加完整替换接口，或采用与 `auto_model_weight.go` 类似的独立配置容器；不要通过多次公开方法拼出“原子更新”。
- getter 深拷贝 map 和每个模型列表，调用方不能修改在线配置。
- 非法配置不改变原配置。并发读只能看到完整旧值或完整新值，不能看到空中间态或混合值。
- 本文件的 JSON 实际解析／序列化改用 `common.Unmarshal`／`common.Marshal`，清理直接调用 `encoding/json` 的旧写法。

## 5. AUTO-03：重排状态与派发前资格边界

### 重排返回值

改为有明确状态的结果，至少区分：

| 状态 | 处理 |
| --- | --- |
| 无需重排，例如没有已尝试路线 | 继续现计划单调前进，不重新从队首抽取 |
| 重排成功且有候选 | 替换计划，从新队首开始 |
| 重排成功但无候选 | 清空／失效当前计划，结束候选尝试，绝不回退旧路线 |
| 刷新失败 | 记录诊断并停止继续派发，保留真实最后上游错误；不得以失败结果假充“无候选”或继续未经完整复验的旧计划 |

### 最终资格复验

- 提供可复用的候选资格检查，首次绑定和每次重试派发共用。
- 对路线所属分组读取完整最新候选配置及模型权重，拒绝名单外、显式空名单、零／非法模型权重的路线。
- 保留令牌权限、分组权限、启用 ability、渠道状态、冷却、请求级排除、已试路线及端点适配检查，并确认模型仍有计费资格。
- 资格检查不使用历史评分证明可用，不重新引入独立随机选渠。
- 明确复验的快照时点；不宣称配置能在网络调用已经开始之后撤回该请求。
- 派发前被拒绝的路线进入本请求本地跳过集合，并有限前进；重排不得反复放回同一失效路线。新配置不能让单个请求无限扩张候选池。

## 6. AUTO-04：真实派发预算与本地跳过分离

- `AutoModelMaxAttempts` 约束真实进入上游请求回调的次数，含首次；连接失败和上游 429 属于真实派发，必须计数。
- 本地 RPM／每日限额拒绝、派发前资格失效及取消，不占真实派发预算；本地请求体或计费错误仍遵守原有停止规则，不能借“不占预算”任意重试。
- 推荐使用“暂占预算 → relay 返回后按 dispatch 标记确认／撤销”的两阶段记账；禁止没有 dispatch 时仍永久消耗预算。预算在首次真实派发确认时冻结，渠道 override 和换模型／组不能放大它。
- `BeginAttempt`／`MarkUpstreamDispatch`／`HasUpstreamDispatch` 的时序必须一致，下一次尝试不能继承上次的派发标记；相关 HTTP、Responses、Claude、Gemini、WebSocket 路径一并审阅。
- 分离已派发三元组、本地失效路线、渠道级本地限额跳过；不要为了释放预算而让本地 RPM 已满渠道重新入池。
- 保留独立有限的本地遍历约束、请求取消约束及路线去重；不靠提高预算掩盖问题。
- 示例交付结果：前四条路线都本地 RPM 拒绝、第五条可用时，在候选范围及请求状态允许的情况下，第五条能够派发，之前四次不计真实上游尝试。

## 7. AUTO-05：评分快照同刻度排序与真实确认

- `observed_at` 保留真实观测时间，继续用于衰减和恢复；不能靠人为增加时间戳／等待墙钟来代替观测排序，不能在保存时刷新观测时间。
- 增加独立的快照排序元数据，建议 `observation_seq` 与 `writer_id`：同进程同三元组在评分锁内递增序号，实例标识按进程生成；恢复旧行时为新字段提供兼容初值。
- 冲突比较优先真实 `observed_at`，同刻度再用明确的序号／实例标识规则打破并列。多实例仍是选一个快照，不合并 EWMA；跨实例同刻度顺序是确定性的冲突规则，不冒充全球严格事件顺序。
- 正常反馈、“清除负面效果”、手动赋分及其他评分更新入口必须共用元数据分配规则。采集时间应与锁内更新时序一致。
- SQLite／PostgreSQL 与 MySQL 的 upsert 条件保持一致，MySQL 继续注意赋值先后；不能简单将严格 `<` 改为 `<=`，否则延迟旧快照可覆盖新快照。
- 数据库入口返回足以区分“已写入／库内完全相同／已被更新快照取代／失败”的结果，或者读取关键行核实。批量总 RowsAffected 不能证明每一条已写入。
- `p.saved` 只确认数据库已经接纳或完全相同的快照；被较新快照取代的批次单独标记，不伪装成已保存，也不要无止境重写。比较时包含所有排序元数据及实际评分内容。
- schema 使用 GORM 跨库增列，保留旧评分行版本兼容或明确定义迁移；清理依赖“必须等到时间前进才能接受新观测”的失效源码假设。

## 9. 安全修改与泄露处置要求

### 9.1 凭据字面量与生产默认值

- 将 `common/str.go:250` 的完整 key-shaped 示例改为明显不可用的脱敏占位说明；保留实际脱敏算法，不改变受保护项目名称、品牌、版权和归属。
- 测试和文档只用明显不可用的合成值，不从用户数据库、真实请求、浏览器会话或 OAuth 响应复制凭据。
- 部署配置去掉可直接投入生产的固定密码默认值，改为必须由本地环境／secret 文件提供，并保持数据库连接与容器密码配置一致。生产配置缺少凭据时明确失败，不静默采用公开默认值。
- Redis 带密码 URI、SQL DSN 等配置也纳入检查；不能只搜索 `API_KEY`。
- 不把上游 API key、令牌、refresh token、JWT／session secret、OAuth client secret、签名私钥加入 auto 分数、冷却原因、路由日志、审计记录或前端诊断字段。
- 新增或修改的错误／路由日志先脱敏；不以整份 channel、请求 header、环境变量或客户端配置作为调试输出。

### 9.2 Git／Docker／发布边界

- `.gitignore` 与 `.dockerignore` 分别覆盖实际存在或可能生成的本地 `.env.*`、密钥／证书私钥、服务账号文件、凭据导出、SQLite／备份、日志／HAR、工具数据库与打包缓存。
- 保留 `.env.example` 等明确无真实凭据的模板；不要将正常代码文件如 `service/codex_credential_refresh.go` 仅因名称含 credential 就排除。
- 已受跟踪文件不能靠新增 ignore 清除，应单独处理；发现真实敏感文件时报告范围后再做必要的取消跟踪，不删除用户本地凭据。
- 发布附件使用产物白名单，不上传整个工作区、数据目录、调试日志或源码缓存。已有 Release／Actions 附件是否含敏感内容，需要单独核实，不能从 workflow 文件推断已发布附件绝对安全。
- 核查前端可公开环境变量；不得将后端上游密钥放入 `VITE_*` 或浏览器 bundle。
- 增加独立密钥扫描配置和提交／PR 安全门禁，可使用 Gitleaks 等工具；报告默认脱敏。禁止宽泛地忽略全部注释、全部文档或全部测试；例外按具体规则／位置记录理由，不把真实密钥本体写进 allowlist。
- 权限允许时核查 GitHub Secret Scanning／Push Protection 的可用性与启用状态；这属于安全防泄露要求，不替代本地检查。无权限时明确未完成项，不宣称已开启。
- 安全门禁不得依赖主动调用真实上游验证密钥，也不得将源码或疑似凭据上传到第三方扫描服务。

### 9.3 一旦确认真实凭据已经推送

1. 先报告凭据类型、脱敏指纹、文件／提交／远端位置，不展示原文。暂停继续发布涉及它的内容。
2. 由凭据所有者在供应商端撤销并轮换，检查调用、费用、权限及异常访问。**删代码或删历史不能替代轮换。**
3. AI 不得拿疑似密钥尝试认证；真实轮换、远端删除、历史重写或强推必须获得明确批准。
4. 轮换后清除当前源码中的真实值，检查分支／标签／PR／fork／日志／附件的影响范围；历史清理方案单独确认，并协调协作者重新同步。
5. 不保证能够抹除 GitHub 缓存、fork、他人克隆；若无法核实某个外部副本，交付时如实列出。

## 11. 实施顺序与交付标准

### 顺序

先复核安全风险并替换完整 key-shaped 示例 → 原子发布候选配置 → 区分重排状态和补齐资格复验 → 分离本地跳过／真实派发预算 → 原子并发摘除与缓存提交时序 → 修复快照排序／确认 → 完成防泄露边界和旧引用清理。
